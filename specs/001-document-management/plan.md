# Implementation Plan: Document Upload and Management

**Branch**: `001-document-management` | **Date**: 2026-10-20 | **Spec**: [spec.md](spec.md)
**Input**: `specs/001-document-management/spec.md` derived from `StakeholderDocs/document-upload-and-management-feature.md`

## Summary

Deliver secure, offline document upload, organization, search, preview/download, sharing, task/project integration, dashboard summaries, and administrator reporting. Extend the existing Blazor Server application with EF Core document metadata, private local file storage, an optional local malware-scanning adapter, and service-level authorization. Research decisions and alternatives are recorded in [research.md](research.md).

## Technical Context

**Language/Version**: C# / .NET 10 (`net10.0`)  
**Primary Dependencies**: ASP.NET Core Blazor Server; EF Core SQLite 10; xUnit and `Microsoft.NET.Test.Sdk` in a new test project  
**Storage**: SQLite for metadata; local filesystem under configurable `AppData/uploads` outside `wwwroot` for file bytes  
**Testing**: xUnit service tests using EF Core SQLite in-memory with a persistent open connection, scanner/storage fakes, plus the manual end-to-end scenarios in [quickstart.md](quickstart.md)  
**Target Platform**: Cross-platform .NET 10 local training host; no cloud services or network dependency for document storage  
**Project Type**: Single Blazor Server web application plus a focused test project  
**Performance Goals**: 25 MB upload within 30 seconds; 500-document lists and search within 2 seconds; supported preview within 3 seconds  
**Constraints**: 25 MB per file; allowlisted types; private local storage; warn-and-allow when malware scanning is unavailable/inconclusive, reject confirmed infections; authorization on all access  
**Scale/Scope**: Existing mock users/projects/tasks; 500 documents per tested list; no production availability or compliance target

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Evaluation |
|---|---|
| I. Training-First Scope | Pass. The feature remains offline and training-only. Warn-and-allow for unavailable/inconclusive scanning is explicitly accepted in the spec and must never be described as a clean scan or production-grade protection. |
| II. Layered Application Design | Pass. Razor pages use `IDocumentService`; storage and optional scanning use narrow interfaces; EF Core access remains in services. |
| III. Authenticated Access and User Isolation | Pass. Use authenticated claims for identity, centralize authorization, and re-check access for list/search/mutations/download/preview. |
| IV. Offline Persistence and Data Integrity | Pass. SQLite metadata and local private filesystem storage; use staging, compensation, validation, and schema migrations. |
| V. Verifiable, Incremental Delivery | Pass. Trace work to the five spec stories; add SQLite-backed service tests and manual quickstart checks; build and test before completion. |

**Gate result**: No constitution violations. The approved scan fallback is a documented training risk, not an unapproved exception.

### Post-Design Re-check

Pass. The data model preserves hard-delete audit history, file content stays outside `wwwroot`, authorization is service-enforced on all read paths, and migration/test work is included. No additional constitution deviations were introduced.
